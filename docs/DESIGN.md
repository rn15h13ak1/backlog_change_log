# 設計仕様書

このツールを **保守・改修する人** 向けの文書です。

使い方・設定項目の一覧は [README.md](../README.md) にあります。
**この文書では使い方を再掲しません。** 二重に書くと必ず食い違うためです。
ここに書くのは「なぜそうなっているか」と「どこを触ればよいか」です。

---

## 1. 前提

このツールの設計判断は、次の 3 つの前提から導かれています。
**改修時はこの前提が変わっていないかを最初に確認してください。**

| 前提 | 帰結 |
|---|---|
| **日次の記録** が主目的（前日にどの課題のどの項目が変わり、最終的に誰の担当か） | 誰が何から何に変えたかは載せない。担当者は「その日の終わり」の値を載せる。複数のプロジェクトも 1 日 1 件にまとめる |
| **Backlog に書き込む** ツール（コメントを投稿する） | 二重投稿を避ける。ただし抜けよりは重複を選ぶ |
| **定期実行で無人** のまま動かす | 欠けた記録を「出力済み」として残さない。出力しなかった日は Exit code で知らせる |

3 つ目が特に効いています。遡りきれない日や形の違う応答の日を投稿しない、
出力しなかった日に Exit code `3` を返す、といった判断はすべてこれが根拠です。

## 2. 全体構成

```
backlog_change_log.py    入口（引数・設定・ロック）
check_api.py             診断の入口
menu.py / menu.bat       対話メニュー（上の 2 つを subprocess で呼ぶ）
change_log/
  runner.py              通しの処理（クライアントを引数で受け取る）
  client.py              Backlog API
  marker.py              目印の書式、出力する日の決定
  collect.py             アクティビティの取得と集約
  state.py               その日の終わりの値の逆算
  render.py              コメント本文
  config.py / lock.py / runtime.py / diagnose.py / core.py
```

### 依存の向き

- **API を呼ぶのは `client.py` だけ。** `runner.py` と `diagnose.py` はクライアントを引数で受け取り、
  テストでは `tests/fakes.py` の `FakeClient` を渡します。`runner.Client`（Protocol）が両者の約束です
- `marker.py` / `collect.py` / `state.py` / `render.py` は API を知りません。辞書を受け取って値を返すだけです
- 入口と同じ名前のパッケージにすると setuptools と mypy が取り違えるため、パッケージ名は `change_log` です

### 実行環境の確認を先に行う

入口（`backlog_change_log.py` / `check_api.py`）は、ほかの import より先に `change_log/runtime.py` で
Python の版と依存を確かめます。 **`runtime.py` は 3.9 でも読める書き方に保ってください**
（`str | None` などを使わない）。崩すと、古い Python で案内が出る前に `TypeError` で落ちます。

## 3. 処理の流れ

1. 記録先の課題を取得し、プロジェクトと記法を得る
2. 記録先のコメントを新しい順に読み、自分が投稿した `対象日:` の行を最初の 1 件見つけたら止める
3. 出力する日を決める（初回は前日だけ、以降は最新の日の翌日〜前日、7 日を超える分は捨てる）
4. 追跡するプロジェクトごとに、アクティビティを新しい順に、出力する最初の日の 0:00 まで取得する
5. 出来事に展開し、記録先の課題を除く。形の違うものは読み飛ばして日時を控える
6. 出てきた課題の現在の値を、プロジェクトごとにまとめて取得する
7. **どれか 1 つのプロジェクトで** 遡りきれなかった日、形の違うものがあった日を、出力する日から外す
8. 古い日から、プロジェクトごとに集約 → 担当者・件名を逆算 → 1 件の本文にまとめる → 投稿、を繰り返す
9. 当日分を同じ手順で作り、標準出力に出す

### 段階の意図

- **アクティビティは 1 回だけ取得します（4）。** 日ごとに取りに行くと、補う日が増えるほど同じページを
  何度も読むことになります。取得した中に「その日より後の変更」も含まれるので、8 の逆算に追加の呼び出しは要りません
- **出力する日を先に決めます（3）。** 決まれば取得をどこで止めるかが決まり、読む量が最小になります
- **コメントは最新の目印で読むのをやめます（2）。** 毎日実行していれば 1 ページ目で終わります

## 4. Backlog API への依存

呼んでいるのは 6 つのエンドポイント（7 種類の呼び出し）です。
**このツールの不具合の大半は、ここの理解のずれから来るはずです。**

| 用途 | エンドポイント | メソッド |
|---|---|---|
| API キーの持ち主 | `/users/myself` | GET |
| 記録先の課題 | `/issues/:issueIdOrKey` | GET |
| 記録先の記法、追跡するプロジェクトの ID | `/projects/:projectIdOrKey` | GET |
| 記録先のコメント | `/issues/:issueIdOrKey/comments` | GET |
| プロジェクトのアクティビティ | `/projects/:projectIdOrKey/activities` | GET |
| 現在の課題（担当者・件名） | `/issues`（`id[]` 指定） | GET |
| コメントの投稿 | `/issues/:issueIdOrKey/comments` | POST |

### 応答のどのフィールドに依存しているか

**Backlog 側の仕様とのずれはテストでは検知できません。** `check_api.py` で確かめます（[8. テスト方針](#8-テスト方針)）。

| フィールド | 用途 |
|---|---|
| アクティビティの `type` / `created` | 種別の判定、日の振り分け、取得を止める位置 |
| `content.id` / `content.key_id` / `content.summary` | 課題の識別、課題キーの組み立て、削除された課題の件名 |
| `content.changes[].field` / `old_value` / `new_value` | 変わった項目名、その日の終わりの値の逆算 |
| `content.comment.content` | コメントが書かれたかの判定 |
| 一括更新の `content.link[]`（`id` / `key_id` / `title`）と `content.changes[]` | 一括更新を課題ごとに展開する |
| コメントの `createdUser.id` / `content` | 自分が投稿した目印の検出 |
| プロジェクトの `projectKey` / `textFormattingRule` | 課題キーの組み立て、記法の切り替え |
| 課題の `summary` / `assignee.name` | 現在の値（逆算の起点） |

### 押さえておくべき API の性質

- **削除された課題は課題一覧に出ない。** そのため変更はアクティビティから読みます（[5.1](#51-変更はアクティビティから読む)）
- **アクティビティの API は日付で絞れない。** 新しい順にページを送り、目的の日の 0:00 より前に達したら止めます
- **担当者の変更は `assigner` という項目名で返る（公開仕様による。未確認）。** 値は ID ではなく表示名です
- **削除済みの課題は `/issues` で取れない。** 後日削除された課題の担当者は、アクティビティに残る値から求めます
  （無ければ「不明」）

## 5. 設計判断と根拠

### 5.1 変更はアクティビティから読む

課題一覧の `updatedSince` を使えば更新された課題は分かりますが、 **削除された課題が出てきません。**
また「どの項目が変わったか」も分かりません。アクティビティなら作成・更新・削除・コメントがすべて
残り、変わった項目名も持っています。

### 5.2 出力済みの日はコメントの目印で判定する

状態をファイルに持つと、別の端末から実行したときや、ファイルを消したときに食い違います。
記録そのもの（コメント）に目印を残せば、記録と状態が一致します。
判定は自分が投稿したコメントに限ります。他人が同じ書式の行を書いても誤認しないためです。

### 5.3 最新の日の翌日から出力し、途中の抜けは補わない

当初は「最も古い出力済みの日から前日までの抜け」を補う案でしたが、利用者の判断で
**最新の日の翌日から** にしました。コメントを最新の目印まで読めば済み、処理が軽いためです。
日は古い順に投稿するので、通常の運用で途中に抜けは生じません。

### 5.4 初回は前日だけ、補うのは最大 7 日

初回に過去へ遡ると、大量のコメントを一度に投稿します。上限を超えた日は **次の実行でも出力しません**
（最新の日が進むため）。代わりに Exit code `3` で知らせます。

### 5.5 担当者・件名は、その日の終わりの値を逆算する

実行時点の値を載せると、まとめて補う日のすべてに今日の担当者が並びます。
**現在の値から始め、その日より後で最初に起きた変更の「変更前の値」を取る** ことで、
その日の終わりの値になります。必要な変更は 4 の取得に含まれているので、追加の呼び出しは要りません。

### 5.6 コメントの投稿は再送しない

通信断や 5xx の後に再送すると、投稿済みだった場合に同じコメントが二重に残ります
（`../excel_to_backlog` と同じ判断）。失敗したらそこで止め、残りの日は次回に回します。
429 も再送しません。 **1 日 1 件しか投稿しないので、再送しない損失が小さい** ためです。

### 5.7 変更が無い日も投稿する

投稿しないと、その日に目印が残らず、次回も「未出力」と判定されます。
「変更なし」も記録の一部です。

### 5.8 欠けているかもしれない日は投稿しない

[前提](#1-前提)の 3 つ目による判断です。次の日は投稿しません。

| 状況 | 判定 |
|---|---|
| アクティビティを最後まで読んでも、その日の 0:00 に届かない | 取得できる範囲の外かもしれない。ただし次のどれかなら **履歴は揃っている** とみなす（下記） |
| 形の違うアクティビティがあった | その日の変更が欠けている。日時も読めなければ、すべての日を止める |

履歴が揃っているとみなす根拠は次の 3 つです。

- **記録先の課題の作成が見えている** （記録先のプロジェクトのみ）
- **課題番号 1 の課題の作成が見えている。** プロジェクトで最初の課題で、削除されていても履歴には残ります。
  記録先の課題が無いプロジェクトを追跡するために足しました
- **アクティビティが 1 件も無い。** 取得できる範囲の外だけに変更がある、とは考えにくいためです。
  変更の無いプロジェクトを追跡すると、これが無ければ毎日すべての日が止まります

**どれか 1 つのプロジェクトで当てはまれば、その日ごと投稿しません** （[5.13](#513-欠けているかもしれない日はプロジェクトを跨いで日ごと止める)）。

### 5.9 記録先の課題は対象外

記録先には毎日このツールがコメントを投稿します。対象に含めると、毎日「コメント」の更新として載ります。

### 5.10 同時実行は記録先ごとのロックで防ぐ

2 つの実行が同時に最新の目印を読むと、同じ日を二重に投稿します。OS のファイルロック
（`fcntl` / `msvcrt`）を使うので、異常終了しても残りません。ロックファイルは一時フォルダに置きます。
リポジトリに置くと `.gitignore` が要り、`--config` で記録先を使い分けたときに場所を共有できないためです。
`--dry-run` は投稿しないのでロックを取りません。

### 5.11 API キーは設定ファイルに書かない

[共通規約 C](../../ws-conventions/README.md#設定ファイル) による判断です。`.env` を探す順は
`../backlog_issue_sheet` に揃えています。

### 5.12 複数のプロジェクトは 1 つの課題・1 日 1 件のコメントにまとめる

記録先をプロジェクトごとに分ける案、プロジェクトごとに別のコメントにする案もありましたが、
利用者の判断で **1 つの課題・1 日 1 件** にしました。コメントの数が増えず、1 日分を 1 か所で読めるためです。
プロジェクトが 1 つのときは見出しを付けず、複数対応の前と同じ形にしています。

目印（`対象日:`）は日ごとに 1 つのままです。プロジェクトを目印に含めないので、出力済みかどうかも
日ごとに 1 つです。 **途中でプロジェクトを足しても、足したプロジェクトの過去の日は出力されません。**

### 5.13 欠けているかもしれない日は、プロジェクトを跨いで日ごと止める

1 日 1 件のコメントなので、欠けたプロジェクトだけを抜いて投稿すると、その日に目印が残ります。
次回は出力済みと判定され、 **抜けたプロジェクトの分を後から補えません。** [前提](#1-前提)の 3 つ目により、
その日ごと止めます。

### 5.14 記録先のプロジェクトは、一覧に書いたときだけ追跡する

記録先の課題を、追跡しないプロジェクト（記録用のプロジェクトなど）に置けるようにするためです。
一覧を省略したときは、記録先のプロジェクトだけを追跡します。複数対応の前の `config.yaml` はそのまま動きます。
コメントの記法は、コメントを書く記録先のプロジェクトに合わせます。

### 5.15 メニューは本体を別のプロセスで呼び、投稿の前にだけ確認する

`../backlog_issue_cloner` のメニューに揃え、本体を subprocess で呼びます。本体の終了コードと出力を
そのまま使え、メニューの不具合が本体の処理に混ざらないためです。

**確認は「記録する」の前にだけ、メニュー側で 1 回行います。** 本体は定期実行で使うため確認を持ちません
（`backlog_issue_cloner` は本体が確認するので、メニューでは確認しない。ここが違います）。
同じ理由で、前回の選択が「記録する」でも既定にしません。

見出しの表示は、本体の設定の読み込み（`load_config`）を使いません。足りないものがあると終了するため、
メニューでは自前で読み、足りないものを「※」で示します。API キーは `find_api_key` で有無だけを見ます。

## 6. 落とし穴

### 履歴が短いのか、取得範囲の外なのかは区別できない

アクティビティを最後まで読んでも目的の日に届かないとき、当初は一律に「不完全かもしれない」として
投稿しない作りにしました。しかし **作ったばかりのプロジェクトでも同じ状態になり、いつまでも投稿
されません** でした。記録先の課題の作成が見えていれば揃っているとみなすことで区別しています。

複数のプロジェクトに対応した際、 **記録先の課題が無いプロジェクトには、この根拠が使えない** ことが
分かりました。変更の少ないプロジェクトを追跡すると、毎日すべての日が止まります。
課題番号 1 の課題の作成と、アクティビティが 1 件も無いことを根拠に足しています（[5.8](#58-欠けているかもしれない日は投稿しない)）。

### その日より後の読めないアクティビティは、逆算を誤らせうる

形の違うアクティビティがその日より後にあると、担当者・件名の逆算が誤る可能性があります。
ここまで止めると、その日がいつまでも出力されなくなるため止めていません。

### macOS 標準の Python は 3.9

`/usr/bin/python3` で起動すると、`str | None` の型注釈で `TypeError` になります。
`runtime.py` で先に確かめているのはこのためです。

### Markdown の `---` の直前には空行が要る

本文の直後に `---` を置くと、その行が見出し（Setext 形式）として描画されます。
`render.py` は区切り線の前に必ず空行を入れています。

### zsh では、変数に入れた引数が分割されない

`m="main post"` として `$m` を渡すと 1 つの引数になります。`scripts/demo.py` が `run` / `main` / `post`
以外を誤りとして止めるのはこのためです。

## 7. 変更ガイド

**テストと README も同時に直してください。** 実装だけ変えるとドキュメントがずれます。

変更したら次の 3 つを実行してください。

```bash
.venv/bin/python -m pytest -q   # テスト
.venv/bin/ruff check .          # Lint
.venv/bin/mypy                  # 型
```

### md を書くときの体裁

- **`**` による強調の両端は半角スペース。** 句読点や括弧に隣接する場合も入れます。
  日本語文字に直接隣接すると、環境によって強調が描画されないためです
- リンクとアンカーは、共通規約の `../ws-conventions/bin/check-markdown.sh` が検査します

### 項目名の読み替えを増やす

`collect.py` の `FIELD_LABELS` に足します。足さなくても、返ってきた名前がそのまま表示されます。
`check_api.py` の出力に「そのまま表示」と出た項目が候補です。

### コメントの形式を変える

`render.py` を直し、`tests/test_render.py` の期待値を直します。
**`対象日:` の行の書式は変えないでください。** 変えると、それまでの記録を出力済みと判定できなくなり、
初回の扱いに戻ります（`marker.py` の正規表現が判定の根拠です）。

### 出力する日の決め方を変える

`marker.py` の `decide_target_dates` を直します。上限は `core.py` の `MAX_CATCHUP_DAYS` です。

### Backlog API の呼び出しを追加する

1. `client.py` にメソッドを足す（GET は `_get`、書き込みは再送しない `_post`）
2. `runner.py` の `Client`（Protocol）に足す
3. `tests/fakes.py` の `FakeClient` に足す
4. 応答のどのフィールドに依存するかを [4. Backlog API への依存](#4-backlog-api-への依存) に書く。
   確かめられるなら `diagnose.py` にも足す

## 8. テスト方針

```bash
.venv/bin/python -m pytest -q
```

### 何を守っているか

| テスト | 守っているもの |
|---|---|
| `test_marker.py` | 出力する日の決定（初回・連続・補う・7 日の上限）、目印の検出 |
| `test_collect_state.py` | 複数回の更新の集約、コメントだけの更新、一括更新、逆算、形の違う応答 |
| `test_render.py` | コメントの形式（2 つの記法）、分割と目印の位置 |
| `test_runner.py` | 通しの処理（記録先と当日の除外、失敗時の中断、出力しなかった日、Exit code、複数のプロジェクト） |
| `test_client.py` | GET のリトライ、 **POST を再送しないこと** 、ページ送り、API キーが表示されないこと |
| `test_lock.py` | 同時実行の防止（別のプロセスが持つロックも含む） |
| `test_menu.py` | メニューの入力、組み立てた引数を本体が受け付けること、投稿前の確認、前回の選択、見出しの表示 |
| `test_config.py` / `test_runtime.py` / `test_diagnose.py` | 設定と API キー、実行環境の確認、診断 |

`test_client.py` は、POST にリトライを入れる・ページ送りの `- 1` を外す、という変異で落ちることを確かめています。

### 対象外

| 箇所 | 理由 |
|---|---|
| `ssl_verify: false` の分岐 | SSL コンテキストの構築のみ |
| Windows のロック（`msvcrt`） | macOS では通らない |
| `menu.bat` | Windows でしか動かない |

### テストで守れないもの

**Backlog API の実際の仕様。** テストは `FakeClient` に対して動くため、応答の形や項目名が想定と違っても
検知できません。そのため `check_api.py` という **診断手段** を用意しています。
API 起因の問題は、テストではなく診断と、形の違う応答の日を投稿しない作りで対処する方針です。
